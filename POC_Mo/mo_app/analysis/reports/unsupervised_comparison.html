2.2 ตัววัด

  • จับได้ (detection rate): สัดส่วนของวินาทีที่มีการโจมตีจำลองที่คะแนนเกิน threshold
  • แจ้งผิด/ชม.: จำนวนเหตุการณ์ที่แจ้งบนข้อมูลปกติ (วินาทีห่างกัน ≤ 3 วินาทีนับเป็นเหตุการณ์เดียว เหมือนในระบบจริง) หารด้วยชั่วโมง
  • Threshold แบบ calibrated: ตั้งบนชุด valid ให้แจ้งผิด ≤ 1 ครั้ง/ชม. แล้วนำไปวัดบนชุด test — ทุกโมเดลถูกเทียบที่ระดับแจ้งผิดเท่ากัน จึงยุติธรรม
  • Threshold แบบเดิม (p99.5): percentile 99.5 ของคะแนนบนข้อมูลเทรน (วิธีที่ระบบใช้อยู่เดิม)
  • AUC: ความสามารถแยกวินาทีโจมตีออกจากวินาทีปกติของ test โดยไม่ขึ้นกับ threshold

2.3 ความเท่าเทียมของการทดสอบ

ทุกโมเดลใช้ข้อมูลชุดเดียวกัน การแบ่งชุดเดียวกัน การสุ่มเดียวกัน (seed 0) และการโจมตีจำลองชุดเดียวกัน · โมเดลที่ระบุ "(log)" ใช้ log1p + robust scale (median/IQR จากชุด train) แบบเดียวกัน · "one-sided" = นับเฉพาะค่าที่สูงกว่าปกติ เพราะการโจมตีทำให้ตัวนับเพิ่มขึ้น

3.2 แจ้งผิด vs. จับได้ (ทุก threshold)

แต่ละเส้นคือโมเดลหนึ่งตัวเมื่อเลื่อน threshold · ยิ่งเส้นสูงที่ฝั่งซ้ายยิ่งดี (จับได้มากโดยแจ้งผิดน้อย) · Isolation Forest ทั้งสองแบบแทบเป็นเส้นติดพื้นทุกระดับแจ้งผิด · Ensemble อยู่สูงสุดในช่วงที่แจ้งผิดใกล้ 1 ครั้ง/ชม. ซึ่งเป็นช่วงที่ใช้งานจริง · กราฟนี้เลื่อน threshold บนชุด test โดยตรงเพื่อดูรูปร่างของการแลกกัน ตัวเลขจึงต่างจากตารางที่ตั้ง threshold บนชุด valid เล็กน้อย (ตารางคือค่าที่ใช้ตัดสิน)

3.3 จับได้แยกตามการโจมตี (threshold calibrated)

สิ่งที่เห็นจากตาราง:

  • Ensemble และ GMM จับ deauth/disassoc/assoc flood และ beacon/probe flood แบบแรงได้เกือบ 100% Ensemble จับ RTS/CTS flood แบบแรงได้ 55% (GMM 2%)
  • ไม่มีโมเดลไหนจับ evil twin (BSSID ใหม่) ได้ เพราะช่วง train (15–24 ต.ค.) มี AP ใหม่รอ approve จำนวนมาก ฟีเจอร์ new_bssid_known_ssid จึงสูงเป็นปกติในข้อมูลเทรน
  • ARP spoofing จับได้น้อยทุกโมเดล (≤ 16%)
  • สองกรณีนี้กฎ B จับได้ตั้งแต่ครั้งแรกอยู่แล้ว (new_bssid_known_ssid, arp_ip_mac_flips_10s) ระบบจึงต้องใช้ A และ B ร่วมกัน

4. ทำไม Isolation Forest เดิมจับไม่ได้

Isolation Forest สร้างต้นไม้จากข้อมูลสุ่มต้นละ 256 แถว และแต่ละจุดแบ่งสุ่มเลือก 1 จาก 36 ฟีเจอร์ ฟีเจอร์ที่บอกการโจมตีเป็น 0 ในเกือบทุกวินาที ใน 256 แถวที่สุ่มมาจึงมักเป็น 0 ทั้งหมด (ฟีเจอร์ค่าเดียว → ต้นไม้แบ่งด้วยฟีเจอร์นั้นไม่ได้) และแม้จะแบ่งได้ ก็มีโอกาสถูกเลือกแค่ 1/36 ต่อจุด วินาทีที่มี deauth flood จึงไม่ได้ถูกแยกออกเร็วกว่าวินาทีปกติที่แค่ traffic เยอะ (คะแนนส่วนใหญ่มาจาก len_mean, signal_mean, ปริมาณเฟรม)

5. วิธีตั้ง threshold แบบเดิมใช้กับข้อมูลใหม่ไม่ได้

ถ้าตั้ง threshold ที่ percentile 99.5 ของคะแนนบนข้อมูลเทรนแบบเดิม ทุกโมเดลแจ้งผิดบนข้อมูลใหม่ 3–31 ครั้ง/ชม. (คอลัมน์ "p99.5 เดิม" ในตารางผล) เพราะคะแนนบนข้อมูลที่โมเดลเคยเห็นต่ำกว่าข้อมูลใหม่เสมอ และ traffic เปลี่ยนไปตามเวลา · ข้อสรุป: ต้องตั้ง threshold จากข้อมูลช่วงล่าสุดที่ไม่ได้ใช้ fit

7. ข้อจำกัด

  • การโจมตีเป็นการจำลองที่ระดับฟีเจอร์ การโจมตีจริงอาจกระทบฟีเจอร์อื่นร่วมด้วย (retry, signal, จำนวนอุปกรณ์) ซึ่งน่าจะทำให้จับง่ายขึ้น — ควรยืนยันด้วยการทดสอบโจมตีจริงแบบควบคุมในโซนที่ได้รับอนุญาต
  • ข้อมูลทั้งหมดมาจากจุดติดตั้งเดียว ช่องเดียว · ช่วง train อยู่ก่อน valid/test ประมาณ 2–4 สัปดาห์
  • "แจ้งผิด" นับทุกเหตุการณ์บนข้อมูลที่ถือว่าปกติ ถ้ามีเหตุการณ์ผิดปกติจริงที่กฎ B ไม่จับ จะถูกนับเป็นแจ้งผิดด้วย
  • Autoencoder, LOF และ GMM ใช้ข้อมูล fit บางส่วน (40,000–100,000 แถว) เพื่อให้รันบนเครื่อง sensor ได้

8. การตัดสินใจและสิ่งที่เปลี่ยนในระบบ

เลือก Ensemble เพราะจับได้ใกล้เคียง GMM ตัวเดียว (47%) แต่แจ้งผิดบนข้อมูลใหม่น้อยกว่าครึ่ง (0.40 เทียบกับ 0.83 ครั้ง/ชม.), AUC สูงสุด, และครอบคลุมการโจมตีที่ GMM พลาด (RTS/CTS flood) ด้วย ECOD · Autoencoder จับแบบเบาได้ดีที่สุดเล็กน้อย (31%) แต่จับ beacon/RTS flood ไม่ได้และ fit ช้ากว่า
