# กฎทั้งหมดของระบบตรวจจับ (Live Monitor)

อัปเดต: 2026-10-13 · โค้ดอ้างอิง: `analysis/features.py`, `analysis/detector.py`, `monitor.py`
รายละเอียดที่มาและผลทดสอบ: `anomaly_detection_notes.md`

ระบบดูข้อมูลเป็น **ช่วงละ 1 วินาที** (รวมหลายเฟรม) แล้วส่งให้ตัวตรวจ 2 ตัวที่ทำงาน **คู่ขนาน**
(ไม่ต่อกันแบบ A → B เพราะ A มองไม่เห็นสิ่งที่ไม่เคยเกิดใน baseline)

---

## 1. กฎตรวจจับ (ตัวตรวจ B)

threshold ทุกตัวคำนวณใหม่ทุกครั้งที่เทรน จากข้อมูล baseline ที่ "สะอาด" (ดูข้อ 4)

### 1.1 แจ้งเตือนตั้งแต่ครั้งแรกที่เกิด

| ฟีเจอร์ | จับอะไร | ทำไมเจอครั้งเดียวก็แจ้ง |
|---|---|---|
| `new_bssid_known_ssid` | **Evil twin**: AP ใหม่ใช้ชื่อเครือข่ายที่ป้องกัน | AP ขององค์กรไม่เปลี่ยน BSSID เอง — **แจ้งครั้งเดียวต่อ BSSID** แล้วเข้ารายการ "รอยืนยัน" (ดู 1.5) |
| `deauth_seq_out_of_order` | **Deauth/disassoc ปลอม**: seq ไม่ต่อเนื่องกับตัวนับของ AP | deauth จริง 100% อยู่ระหว่าง seq ของ beacon ก่อน/หลัง (ยกเว้น retry ย้อนหลังได้ ≤ 64) |
| `arp_ip_mac_flips_10s` | **ARP spoofing**: IP เดิมเปลี่ยน MAC | ใน baseline ไม่มี IP ไหนเปลี่ยน MAC เลย (ถ้าวันหนึ่ง baseline มี → เปลี่ยนเป็นเกณฑ์ > 2) |

### 1.2 แจ้งเตือนเมื่อเกินเกณฑ์ปริมาณ (flood)

เกณฑ์ = ค่าที่มากกว่าระหว่าง (ค่าสูงสุดใน baseline × 1.2) กับ (ค่าขั้นต่ำด้านล่าง)

| ฟีเจอร์ | จับอะไร | ค่าขั้นต่ำ |
|---|---|---:|
| `deauth` | Deauth flood (ต่อวินาที, ตัด retry) | 10 |
| `disassoc` | Disassociation flood | 10 |
| `auth` | Authentication flood | 10 |
| `assoc_req` | Association flood | 10 |
| `deauth_to_one_client_10s` | **Deauth เจาะจงเครื่องเดียว** ใน 10 วินาที (ไม่นับ frame ที่ seq ยืนยันว่า AP ส่งเอง) | 5 |
| `tsf_offset_switches` | **Evil twin ปลอม BSSID**: นาฬิกา 2 ชุดหลัง BSSID เดียว | 3 |
| `arp_ips_per_mac_60s` | MAC เดียวอ้างหลาย IP ใน 60 วินาที | 3 |

### 1.3 กฎทั่วไป: เกินค่าสูงสุดใน baseline × 1.2

ใช้กับฟีเจอร์ที่เหลือทั้งหมด (ดูเฉพาะ**ขาขึ้น** เพราะการโจมตีเพิ่ม frame/AP/flag)

- **ฟีเจอร์ที่ผูกกับประเภทการโจมตี** → ระดับ `rule` เช่น `beacon`/`n_ssid`/`n_bssid` (beacon flood),
  `rts`/`cts` (jamming), `probe_req`, `retry_ratio`, `dhcp`, `mdns`, `ssdp`, `arp`, `bssid_signal_range`, `bssid_beacon_rate` ฯลฯ
- **ฟีเจอร์ทั่วไป 8 ตัว** (`signal_mean`, `len_mean`, `mgmt`, `ctrl`, `data`, `protected_ratio`, `n_dest_mac`, `tcp`)
  → ระดับ `info` (ไม่ชี้การโจมตีแบบใดแบบหนึ่ง เช่น มีมือถือวางใกล้ sensor หรือคนโหลดไฟล์)

### 1.4 SSID ที่ป้องกัน

SSID ที่เห็นใน **≥ 90% ของไฟล์ 5 นาที**ทั้งหมด (ตอนนี้: KUWIN, KUWIN-IOT, eduroam, AIS ×2)
hotspot ที่โผล่มาชั่วคราวไม่ถูกป้องกัน จึงไม่ทำให้เกิด evil twin alert เมื่อเปิดใหม่ด้วย MAC สุ่ม

### 1.5 AP ใหม่รอยืนยัน (pending)

- BSSID ใหม่ที่ประกาศ SSID ที่ป้องกัน → แจ้ง evil twin **ครั้งแรกที่เห็นเท่านั้น** แล้วเข้ารายการบนหน้าเว็บ
  (เดิมแจ้งทุกวินาที: 11,541 ครั้งใน 4 วันจาก AP จริงของมหาวิทยาลัย `a4:6c:2a…`, `cc:16:7e…`)
- ระหว่างรอ: **ไม่ถูกเรียนรู้เป็น known** ไม่ว่าจะได้ยินนานแค่ไหน (กัน evil twin จริงกลายเป็นของปกติ) แต่วินาทีอื่นยังใช้เทรนได้
- ผู้ดูแลกด **Approve** ครั้งเดียวต่อ AP (ควรให้ฝ่าย IT ยืนยัน) → ถูกเพิ่มเป็น known
- ข้อสังเกตบนหน้าเว็บ: AP จริงมักประกาศหลาย SSID, MAC มาจากผู้ผลิต (ไม่ใช่ MAC สุ่ม — ถ้าสุ่มจะขึ้นป้ายแดง)

## 2. ตัวตรวจ A (Isolation Forest)

- ดูทุกฟีเจอร์รวมกัน หา "ส่วนผสม" ที่ไม่เคยเห็น
- threshold = percentile 99.5 ของคะแนนบนข้อมูลเทรน
- **บอกประเภทไม่ได้** → ขึ้นว่า "Unusual combination of traffic features (model A — type unknown)"

---

## 3. ระดับการแจ้งเตือน (confidence)

| ระดับ | เมื่อไหร่ | นับเป็น false alarm | ตัดออกจากการเทรน |
|---|---|:---:|:---:|
| `rule` | กฎ B ที่ผูกกับประเภทการโจมตี | ✅ (ยกเว้นถ้า A แจ้งพร้อมกัน) | ✅ |
| `info` | กฎ B กับฟีเจอร์ทั่วไปเท่านั้น | ❌ | ❌ |
| `low (still learning)` | A อย่างเดียว ขณะ A ยังไม่ได้รับความเชื่อถือ | ✅ | ❌ |
| `normal` | A อย่างเดียว ขณะ A ได้รับความเชื่อถือแล้ว | ✅ | ✅ |

- คอลัมน์ "By": `A`, `B`, หรือ `A+B` (ทั้งสองแจ้งพร้อมกัน)
- วินาทีที่ติดกัน (ห่าง ≤ 3 วินาที) จากตัวตรวจและระดับเดียวกัน รวมเป็นเหตุการณ์เดียว
- ตัวเลข "Alerts, last hour" บนหน้าเว็บไม่นับ `info` (แสดงแยกเป็น "info notices")

---

## 4. การเรียนรู้ (เทรน)

**เมื่อไหร่:** ตอนแอพเปิด, ตอน import baseline, ทุก 10 นาทีระหว่าง monitor ทำงาน,
และตอนโค้ดฟีเจอร์เปลี่ยน (`FEATURE_VERSION`) → คำนวณฟีเจอร์ใหม่จากไฟล์ดิบทั้งหมดก่อน

**วิธี:** เทรนใหม่ทั้งหมดตั้งแต่ต้น (ไม่ fine-tune) จากข้อมูลทุกวินาทีที่เก็บไว้ ยกเว้นข้อ "anti-poisoning"

**Anti-poisoning:** ไม่เรียนรู้วินาที (±5 วินาที) ที่ถูกแจ้งระดับ `rule` หรือ `normal`
→ การโจมตีที่ตรวจเจอจะไม่ถูกเรียนรู้เป็น "ปกติ"
→ `info` และ `low` ยังเรียนรู้ได้ (ไม่งั้นช่วงแรกที่ A ยังแจ้งผิดถี่ ระบบจะไม่ได้เรียนรู้อะไรเลย)

**ข้อมูลที่เรียนรู้จากวินาทีที่ไม่ถูกแจ้งเตือนเท่านั้น:** คู่ SSID/BSSID ที่รู้จัก, การจับคู่ IP→MAC ของ ARP

## 5. Brain Power

**Brain Power = 50% × ความครอบคลุม + 25% × ความนิ่งของ threshold + 25% × คะแนน false alarm**

| ส่วน | วิธีคำนวณ |
|---|---|
| ความครอบคลุม | 168 ช่องชั่วโมงของสัปดาห์ (เวลาเครื่อง) แต่ละช่องเต็มที่ 30 นาที → ค่าเฉลี่ยความเต็ม |
| ความนิ่ง | เทียบ threshold ทุกตัวกับรอบที่บันทึกก่อนหน้า: 1 − 5 × (ค่ามัธยฐานของ % ที่เปลี่ยน), เฉลี่ย 3 รอบล่าสุด; บันทึกเฉพาะเมื่อข้อมูลเทรนเพิ่ม ≥ 10% |
| false alarm | ดูข้อ 6; ≤ 1/ชม. = 100%, ≥ 30/ชม. = 0%, ระหว่างนั้นแบบ log |

ระดับ: Learning < 30 ≤ Calibrating < 70 ≤ Almost ready < 95 ≤ Ready

## 6. การวัด false alarm

- **สมมติฐาน:** ทุกการแจ้งเตือนช่วงปกติถือเป็น false alarm (ระบบไม่มีทางรู้ว่าอันไหนเป็นการโจมตีจริง
  และไม่พึ่งคนตัดสิน เพราะคนเฝ้าเองก็อาจไม่รู้)
- **วัดบนข้อมูลที่ไม่เคยเห็นจริง:** ทุกครั้งที่เทรน บันทึกช่วง [เทรนครั้งก่อน, ตอนนี้] ซึ่งโมเดลตัวเก่าตัดสินโดยยังไม่เคยเห็น
- **ใช้ค่ามัธยฐานของอัตรารายชั่วโมง** ใน **24 ชั่วโมง**ล่าสุด (ชั่วโมงที่มีข้อมูล ≥ 5 นาที) แทนค่าเฉลี่ย
  (เดิม 6 ชั่วโมง: A ได้รับความเชื่อถือจากกลางคืนที่เงียบอย่างเดียว แล้วไม่ผ่านทันทีที่เช้าวันจันทร์มีคนมา)
  → การโจมตีที่กระจุกอยู่ 1–2 ชั่วโมงไม่ทำให้ดูเหมือนโมเดลแย่ แต่โมเดลที่แจ้งผิดทุกชั่วโมงยังได้คะแนนต่ำ
- **ไม่นับ:** `info` และ `A+B` (สองตัวตรวจเห็นตรงกัน มีแนวโน้มเป็นเหตุการณ์จริง)

---

## 7. ความน่าเชื่อถือของตัวตรวจ A (trust)

- **ได้รับความเชื่อถือ** เมื่อ Brain Power ≥ 50% **และ** false alarm (ข้อ 6) ≤ 5 ครั้ง/ชั่วโมง **และ** วัดได้ ≥ 20 จาก 24 ชั่วโมง
- **ถูกปลด** เฉพาะเมื่อไม่ผ่านเงื่อนไข **ต่อเนื่อง 24 ชั่วโมง**
- เหตุผล: การโจมตีจริงทำให้ A แจ้งเยอะ → คะแนนลด; ถ้าปลดทันที แจ้งเตือนจะกลับเป็น `low` →
  ข้อมูลช่วงโจมตีถูกนำไปเทรน → ระบบเรียนรู้การโจมตีเป็นเรื่องปกติ (ผู้โจมตีใช้เป็นช่องโหว่ได้)
- ตรวจทุกครั้งที่เทรน (ทุก 10 นาที); สถานะแสดงในการ์ด Brain Power

## 8. การป้องกันระบบเอง

| กลไก | ทำอะไร |
|---|---|
| Watchdog | ไม่มี frame 30 วินาที → เปิด monitor mode + ตั้งช่องใหม่ |
| Resume | แอพ/เครื่องรีบูตขณะ monitor ทำงาน → เปิดต่อเอง (ลองทุก 10 วินาที นานสุด 5 นาที); กด Stop = ไม่เปิดต่อ |
| DFS warning | ไม่เห็น SSID ที่ป้องกันบนช่องนี้เกิน 1 นาที → แถบเตือน (AP อาจย้ายช่องหนีเรดาร์) |
| ไฟล์เสียหาย | โหลดไฟล์ที่มี NUL / gzip ขาดท้ายได้; `fsync` ทุกครั้งที่เขียน features/alerts |
| แย่ง adapter | หน้า capture ใช้ interface เดียวกับ monitor ไม่ได้ (409) |
| systemd | service `wifi-capture`: รอด SSH หลุด/รีบูต, restart เองถ้าพัง |

## ข้อจำกัดที่ยอมรับไว้

- การโจมตีที่ **มีแต่ A จับได้** และเกิดขณะ A ยังไม่ได้รับความเชื่อถือ จะถูกเรียนรู้เป็นปกติ
  (การโจมตีที่รู้จักทั้งหมดมีกฎ B คุม ซึ่งตัดออกจากการเทรนเสมอ)
- false alarm ระดับ `rule` ถูกตัดออกจากการเทรน → threshold ของกฎนั้นไม่ขยับ อาจแจ้งเรื่องเดิมซ้ำ (ถ้าเห็นซ้ำบ่อยให้แก้เฉพาะกฎ)
- จับไม่ได้: deauth ที่ลอก seq ของ AP, evil twin ที่ตั้งนาฬิกาตรงกับ AP < 1 ms, การโจมตีบนช่องอื่น, การโจมตีในส่วนที่เข้ารหัส
- เทรนจากข้อมูลทั้งหมดโดยไม่ลืมของเก่า — ถ้าเครือข่ายเปลี่ยนมาก (เปิดเทอม, AP ใหม่) ควรใช้แค่ช่วงหลัง
