## 3. เทียบกับตัวตรวจ A/B

- A/B แจ้งในช่วงเดียวกัน 759 ครั้ง (A 666, B 87, A+B 6) — **ไม่มีครั้งไหนที่ Model C แจ้งด้วย (±5 วินาที)** และแจ้งเตือน 4 ครั้งของ Model C ก็ไม่ตรงกับ A/B เลย
- B แจ้ง deauth/disassoc 7 ครั้ง (targeted, spoofed seq, deauth attack) → proba ของ Deauth/Disas จาก Model C ≈ 0 ทุกครั้ง
- B แจ้ง Evil twin 20 ครั้ง → Model C ให้ Evil_Twin ≈ 1.0 แต่ประเภทนี้ปิดอยู่ และ Evil_Twin สูงตลอดอยู่แล้ว (ข้อ 4) จึงไม่ได้บอกอะไรเพิ่ม

## 4. ปัญหาหลัก: Evil_Twin ครองตั้งแต่ พฤ. 15 ต.ค. 22:10

- ก่อนหน้า ~90–97% ของวินาทีเป็น `normal`; ตั้งแต่ 22:15 Evil_Twin เป็นคลาสที่ proba สูงสุด **80–96% ของวินาที** ต่อเนื่องถึงตอนนี้
- ตรงกับเวลาที่ AP กลุ่ม `a4:6c:2a:a8:11:*` (5 BSSID) โผล่ครั้งแรก (22:10) ฟีเจอร์ `new_bssid_known_ssid` กระโดดจาก 0.004 → ~3.9 ต่อวินาที และค้างอยู่ เพราะ AP ยังอยู่ในรายการ "รอยืนยัน"
- ตอนนี้มี AP รอยืนยัน 25 ตัว (กลุ่ม `a4:6c:2a:*` และ `b0:aa:77:*`) — โมเดลเห็น "BSSID ใหม่ใช้ SSID ที่รู้จัก" ทุกวินาที จึงตอบ Evil_Twin

## สรุป / ข้อเสนอ

1. **ยังไม่ควรเปิดแจ้งเตือน Model C** — ไม่จับอะไรที่ A/B ไม่จับ (0/759) ไม่เห็น deauth ที่ B เจอ และ 3 ใน 8 ประเภทใช้ไม่ได้
2. **ยืนยัน AP ที่รอ (ถ้า IT ยืนยันว่าเป็นของจริง) แล้วดูว่า Evil_Twin ลดลงไหม** — ถ้าลด แปลว่าปัญหาคือฟีเจอร์ `new_bssid_known_ssid` ไม่ใช่ตัวโมเดล
3. ฝั่งเทรน: Krack/Evil_Twin ตอบสูงกับ traffic ปกติของเรา → ควรเพิ่ม baseline ของเรา (ช่วงหลัง 22:10 เป็นตัวอย่าง hard negative ที่ดี) เข้าไปเป็น `normal` แล้วตั้ง threshold ใหม่แบบแบ่งครึ่งเวลา ตามแผนข้อ 3
4. ยังไม่มีการโจมตีจริงในช่วงนี้ จึง**วัด recall บนเครือข่ายเราไม่ได้** — ต้องทดสอบ deauth แบบควบคุมในโซนที่ได้รับอนุญาตถ้าจะวัด
5. Uptime 99.5% พอสำหรับ shadow; ถ้าจะใช้แจ้งเตือนจริงต้องดูช่วงขาดตอนเที่ยง–บ่าย (timeout) ก่อน
