# บันทึกงาน: WiFi Anomaly Detection (unsupervised)

อัปเดตล่าสุด: 2026-10-09

## เป้าหมาย

ตรวจจับการโจมตี WiFi ในโซนที่ได้รับอนุญาต โดยเรียนรู้จาก traffic ปกติ (baseline)
แล้วแจ้งเตือนเมื่อพบความผิดปกติ พร้อมบอกประเภทการโจมตีที่น่าจะเป็น

## สิ่งที่พบเกี่ยวกับการ capture

| เรื่อง | ผล |
|---|---|
| ช่องเดิม (ช่อง 1, ค่าเริ่มต้นของ driver) | แทบมีแต่ beacon, ได้ค่า 45/155 คอลัมน์ |
| สแกนทุกช่อง (2.4 + 5 GHz) | ช่อง 100 (5500 MHz) ได้ข้อมูลมากสุด มี KUWIN, eduroam, KUWIN-IOT, AIS |
| 20 MHz (no HT) vs **40 MHz (HT40+)** บนช่อง 100 | 40 MHz ได้ data เข้ารหัส 18.4/s เทียบกับ 0.13/s, TLS 83 เทียบกับ 2 → **ใช้ HT40+** (ตรงกับ AP จริง) |
| เครือข่ายเปิด (ไม่มี RSN) | KUWIN-IOT, .@ AIS SUPER WiFi → ได้ข้อมูลชั้น app (ARP/DHCP/mDNS/SSDP) |
| PMF (802.11w) | eduroam, KUWIN-IOT, AIS ไม่มี, KUWIN บาง AP มี → deauth ได้ผลจริงในโซนนี้ |
| adapter หลุดจาก monitor mode เอง | เกิด 2 ครั้ง สคริปต์เก็บข้อมูลต้องเช็กและเปิด monitor mode ใหม่ทุกครั้ง |

ตั้งค่าที่ใช้: `iw dev wlx1cbfce71ebe7 set channel 100 HT40+`

## Baseline ที่เก็บแล้ว

- `captures/baseline_ch100_ht40/` — 12 ไฟล์ × 5 นาที (13:03–14:04, 2026-10-08), ~410 MB, **ไม่มี**คอลัมน์ ARP IP/MAC
- `captures/baseline_ch100_ht40_arp/` — 6 ไฟล์ × 5 นาที (14:19–14:50, 2026-10-08), ~220 MB, มีคอลัมน์ ARP
- เก็บด้วย `CaptureSession` ของแอพ, LLC/SNAP dispatch เปิด
- **ความกว้าง 40 MHz เป็นค่ามาตรฐาน** ตอนเก็บ baseline และใช้งานจริงต้องใช้ค่าเดียวกัน
- AP ที่เห็นตลอด: Cisco `00:df:1d:d7:12:a*` (-46 dBm) และ `54:a2:74:e9:65:d*` (-71 dBm)
- hotspot ชั่วคราว: `18/85_5G` (`ae:51:...`, MAC แบบ locally administered)

## การแก้ไขแอพ (`capture.py`, ยังไม่ commit)

1. เพิ่ม `wlan.ra`, `wlan.ta`, `wlan.sa`, `wlan.bssid` (ตีความตาม ToDS/FromDS แบบ Wireshark)
   - `wlan.da` เดิมยังเป็น `addr1` (จริงๆ คือ RA) เพื่อไม่ให้ `n_unique_dest_mac_per_sec` เปลี่ยน
2. เพิ่ม `arp.src.hw_mac`, `arp.src.proto_ipv4`, `arp.dst.hw_mac`, `arp.dst.proto_ipv4` (163 คอลัมน์)
   - ก่อนหน้านี้ IP ของ ARP ถูกใช้ในหน่วยความจำแล้วทิ้ง ตอนนี้เก็บเป็นคอลัมน์ตามแนว `wlan.da`
   - ถ้ากังวลเรื่องความเป็นส่วนตัว เปลี่ยนเป็นเก็บ hash ได้ (ยังเทียบเท่ากัน/ไม่เท่ากันได้)

คอลัมน์ address/IP ใช้จัดกลุ่มเท่านั้น **ไม่ใช้เป็นฟีเจอร์ของโมเดล** ตามกฎ identifier ใน `wifi_capture_poc_spec.md`

## Pipeline (`analysis/anomaly_detect.py`)

ไม่ได้ดูทีละเฟรม: รวมเฟรมเป็นช่วงละ 1 วินาที → 36 ฟีเจอร์ → ตัวตรวจ 2 ตัวทำงาน**คู่ขนาน**

- **A. Isolation Forest** — โมเดล ML บอกได้แค่ปกติ/ผิดปกติ
  - จุดบอด: มองไม่เห็นฟีเจอร์ที่เป็น 0 ตลอดใน baseline (deauth, evil twin) → **ห้ามต่อแบบ A → B**
- **B. ตรวจรายฟีเจอร์** — threshold ทางสถิติ + ตารางกฎ บอกประเภทได้
  - ทั่วไป: เกินค่าสูงสุดใน baseline × 1.2 (ดูเฉพาะขาขึ้น)
  - กลุ่ม flood (deauth/disassoc/auth/assoc): > max(baseline × 1.2, 10/s)
  - evil twin (BSSID ใหม่ + SSID ที่ป้องกัน): เจอครั้งเดียวก็แจ้งเตือน
  - SSID ที่ป้องกัน = เห็นใน ≥ 90% ของไฟล์ baseline (กัน hotspot ชั่วคราว)

### ฟีเจอร์รายเครื่อง/ราย BSSID (v3)

| ฟีเจอร์ | จับอะไร | ค่าปกติ |
|---|---|---|
| `deauth_to_one_client_10s` | deauth แบบเจาะจง | ไม่นับ frame ที่ seq ยืนยันว่า AP ส่งเอง (v2) → ปกติ ≤ 1, เกณฑ์ > 5 |
| `tsf_offset_switches` | evil twin ปลอม BSSID (นาฬิกาสองชุด) | offset นิ่ง ≤ 14 µs, เกณฑ์ > 3 flip/s |
| `bssid_signal_range` | evil twin ปลอม BSSID (คนละตำแหน่ง) | ≤ 11 dB |
| `bssid_beacon_rate` | beacon ซ้ำจาก BSSID เดียว | ≤ 10/s |

หมายเหตุ: นาฬิกา AP vs adapter drift ~7.8 ms / 15 นาที → ต้องเทียบ offset ระหว่าง beacon ติดกัน ไม่ใช่ค่าเฉลี่ยยาว

### ฟีเจอร์ deauth และ ARP (v5)

| ฟีเจอร์ | จับอะไร | ค่าปกติ / กฎ |
|---|---|---|
| `deauth_seq_out_of_order` | deauth/disassoc ปลอม (seq ไม่ต่อเนื่องกับตัวนับของ AP) | deauth จริง 33/33 อยู่ระหว่าง seq ของ beacon ก่อน/หลัง → เจอครั้งเดียวก็แจ้งเตือน |
| `arp_ip_mac_flips_10s` | ARP spoofing (IP เดิมเปลี่ยน MAC) | 30 นาทีไม่มี IP ไหนเปลี่ยน MAC เลย → เจอครั้งเดียวก็แจ้งเตือน (เทียบกับการจับคู่ IP→MAC ที่เรียนจาก baseline) |
| `arp_ips_per_mac_60s` | MAC เดียวอ้างหลาย IP | สูงสุด 3 → เกณฑ์ > 3 |

**เหตุการณ์จริงที่เจอใน baseline ARP (14:22–14:43):** AP Cisco ส่ง deauth reason 7 ไปหามือถือ `6e:ef:f5:...` 87 frame
(มีแค่ 26 frame ที่ไม่ซ้ำ ที่เหลือเป็น retry) seq ต่อเนื่องกับ beacon ของ AP → **AP ส่งเองจริง ไม่ใช่การโจมตี**
(มือถือยังส่งข้อมูลมาเรื่อยๆ ทั้งที่ AP ถือว่าหลุดไปแล้ว) → แก้ให้นับ deauth แบบตัด retry ออก (ตัดซ้ำด้วย ta, ra, seq)

## ผลล่าสุด (v5)

**false alarm บนข้อมูลปกติที่ไม่ได้ใช้เทรน**

| baseline | A. Isolation Forest | B. ตรวจรายฟีเจอร์ |
|---|---|---|
| 1 ชั่วโมง (เทรน 45 / ทดสอบ 15 นาที) | 0 /ชั่วโมง | ~4 เหตุการณ์/ชั่วโมง (SSDP 4 vs train max 3) |
| ARP 30 นาที (เทรน 20 / ทดสอบ 10 นาที) | **~78 /ชั่วโมง** | ~18 เหตุการณ์/ชั่วโมง (probe_req, auth จากเครื่องที่เชื่อมต่อใหม่) |

→ ยิ่ง baseline สั้น false alarm ยิ่งสูง โดยเฉพาะ Isolation Forest ซึ่งไม่เสถียรเมื่อเทรนแค่ 20 นาที

**แทรก frame ปลอมในข้อมูลจริง** (เลือกช่วงที่เงียบ และนับเฉพาะการแจ้งเตือนที่เกิดจาก frame ที่แทรก) — baseline ARP:

| สถานการณ์ | ผล | จับได้ด้วย |
|---|:---:|---|
| deauth ปลอมแบบเจาะจง 1/s × 20 s, seq ของผู้โจมตีเอง | ✅ ทันที | `deauth_seq_out_of_order` |
| deauth ปลอมแบบเจาะจง 5/s × 10 s, seq ของผู้โจมตีเอง | ✅ ทันที | seq + `deauth_to_one_client_10s` |
| deauth ปลอม 1/s, **ลอก seq ของ AP** (ขั้นสูง) | ❌ (✅ บน baseline 1 ชั่วโมง เพราะเกณฑ์ต่ำกว่า) | |
| evil twin ปลอม BSSID, นาฬิกาของตัวเอง (สัญญาณต่างหรือเท่ากันก็ตาม) | ✅ ทันที | `tsf_offset_switches` |
| evil twin ปลอม BSSID, นาฬิกาตรง < 1 ms | ❌ | |
| ARP spoof แบบตอบแข่งกับ gateway จริง | ✅ ทันที | `arp_ip_mac_flips_10s` |
| ARP spoof, gateway จริงไม่ตอบ | ✅ ทันที | `arp_ip_mac_flips_10s` |
| ARP spoof แบบแนบเนียน 1 ครั้ง / 10 s | ✅ ทันที | `arp_ip_mac_flips_10s` |

## ข้อจำกัดที่ทราบ

- การทดสอบทั้งหมดยังเป็นการจำลอง ต้องยืนยันกับการโจมตีจริง (AWID3 pcap หรือ SSID ทดสอบของเราเอง)
- baseline 1 ชั่วโมงยังน้อย ควร ≥ 24 ชั่วโมง, แนะนำ 1 สัปดาห์
- ฟังได้ช่องเดียว (100) ไม่เห็นการโจมตีบนช่องอื่น
- ข้อมูลในส่วนที่เข้ารหัสมองไม่เห็น

- กฎ "เจอครั้งเดียวก็แจ้งเตือน" (evil twin, deauth seq, ARP flip) อิงจาก baseline แค่ 1.5 ชั่วโมง
  ถ้าเก็บนานขึ้นอาจเจอกรณีปกติที่ทำให้แจ้งเตือนผิด เช่น DHCP แจก IP เดิมให้เครื่องใหม่ หรือ AP รีบูต
- ช่อง 100 เป็นช่อง DFS: AP อาจย้ายช่องเองเมื่อเจอเรดาร์ ควรตรวจว่า SSID ที่ป้องกันยังอยู่บนช่องนี้
- ไปสภาพแวดล้อมใหม่: ต้องสแกนช่อง, ตั้งความกว้าง, เก็บ baseline, หา SSID ที่ป้องกัน, และคำนวณ threshold ใหม่
  (ส่วนโค้ด, นิยามฟีเจอร์, ตารางกฎ และเกณฑ์ขั้นต่ำใช้ต่อได้)

## Dashboard POC: Live Monitor (`/monitor`)

เปิดที่ `http://<host>:5000/monitor` (แอพรันเป็น service `wifi-capture`)

- **โครงสร้าง:** `monitor.py` (จับข้อมูลต่อเนื่อง + ตรวจจับ + เรียนรู้), `templates/monitor.html`,
  โค้ดคำนวณฟีเจอร์/ตัวตรวจที่ใช้ร่วมกันใน `analysis/features.py` และ `analysis/detector.py`
  (`anomaly_detect.py` ใช้โมดูลเดียวกัน ตรวจแล้วว่าผลเหมือนเดิมทุกตัวเลข)
- **การทำงาน:** ทุก 5 วินาทีคำนวณฟีเจอร์รายวินาทีจาก frame 90 วินาทีล่าสุด → ตัวตรวจ A + B → แจ้งเตือน
  (รวมวินาทีที่ติดกันเป็นเหตุการณ์เดียว); เทรนใหม่ทุก 10 นาที; **ไม่เรียนรู้จากวินาทีที่แจ้งเตือน (±5 วินาที)** กันการปนเปื้อน
- **Brain Power** = 50% ความครอบคลุมของสัปดาห์ (168 ช่องชั่วโมง, เต็มที่ 30 นาที/ช่อง)
  + 25% ความนิ่งของ threshold (นับเฉพาะเมื่อข้อมูลเทรนเพิ่ม ≥ 10%) + 25% false alarm บนข้อมูลที่ยังไม่ได้เทรน (≤ 1/ชั่วโมง = เต็ม)
  - ระดับ: Learning < 30 ≤ Calibrating < 70 ≤ Almost ready < 95 ≤ Ready
  - การแจ้งเตือนจากกฎ (B) เชื่อถือได้ตั้งแต่วันแรก; การแจ้งเตือนจากโมเดล (A) อย่างเดียวเป็น "low confidence" จนกว่าจะถึง 50%
- **หน้า stat:** สถานะ sensor, Brain Power, KPI (frames/s, data/s, % เข้ารหัส, % retry, สัญญาณ, จำนวนเครื่องส่ง, แจ้งเตือน/ชั่วโมง),
  กราฟ traffic และคะแนนความผิดปกติ 10 นาที, ตารางแจ้งเตือน, แจ้งเตือนตามประเภท 24 ชั่วโมง, AP บนช่อง (protected/known/NEW),
  heatmap ความครอบคลุมรายชั่วโมง, กฎที่ใช้อยู่พร้อม threshold, สุขภาพ sensor + log
- **กันพัง:** เปิด monitor mode ใหม่อัตโนมัติถ้าไม่มี frame 30 วินาที; เตือน DFS ถ้า SSID ที่ป้องกันหายจากช่อง;
  หน้า capture ใช้ interface เดียวกันไม่ได้ขณะ monitor ทำงาน
- **ข้อมูลเก็บที่** `captures/monitor/` (raw `.csv.gz` ทุก 5 นาที, `features.csv`, `alerts.jsonl`, `context.json`)
- **โหมด Replay:** เล่นไฟล์ที่จับไว้ซ้ำแบบ real-time ผ่านตัวตรวจเดียวกัน ใช้สาธิต/ทดสอบได้โดยไม่ต้องมี adapter หรือ root
- **ทดสอบแล้ว:** import baseline 18 ไฟล์ (34 วินาที), replay ~190 frame/s, API ครบ, หน้าแสดงผลจริงใน Firefox (ภาพหน้าจอ),
  กันการใช้ path นอก `captures/` ตอน replay, RAM ~430 MB

## ระดับการแจ้งเตือนและการวัด false alarm (2026-10-09 12:25)

**ระดับ (confidence):**

| ระดับ | เมื่อไหร่ | นับเป็น false alarm | ตัดออกจากการเทรน |
|---|---|:---:|:---:|
| `rule` | กฎเฉพาะทางที่ผูกกับประเภทการโจมตี (deauth, evil twin, ARP ...) | ✅ | ✅ |
| `info` | กฎ B กับฟีเจอร์ทั่วไป 8 ตัว (`GENERIC` ใน `features.py`: signal_mean, len_mean, mgmt, ctrl, data, protected_ratio, n_dest_mac, tcp) | ❌ | ❌ (ให้เรียนรู้เป็นปกติ) |
| `low (still learning)` | A อย่างเดียว, Brain Power < 50 | ✅ | ❌ |
| `normal` | A อย่างเดียว, Brain Power ≥ 50 | ✅ | ✅ |

**False alarm บนข้อมูลที่ไม่เคยเห็น (แก้แล้ว):** เดิมวัดตั้งแต่การเทรนที่บันทึกเป็นประวัติครั้งล่าสุด
แต่ระหว่างนั้นโมเดลถูกเทรนใหม่ทุก 10 นาที → ข้อมูลที่วัด "ถูกเห็นแล้ว" และยิ่งข้อมูลเยอะยิ่งแย่
(1 สัปดาห์ = ห่างกัน ~17 ชั่วโมง/~100 รอบเทรน) → FA ต่ำเกินจริง, Brain Power สูงเกินจริง
→ ตอนนี้: **ทุกครั้งที่เทรน** บันทึกช่วง [เทรนครั้งก่อน, ตอนนี้] ซึ่งโมเดลตัวเก่าตัดสินโดยยังไม่เคยเห็น
(`context.json` → `unseen`), Brain Power ใช้อัตรารวมของ **6 ชั่วโมงล่าสุด** (ต้องมีข้อมูล ≥ 5 นาที)

**ข้อจำกัด:** ระบบไม่รู้ว่าแจ้งเตือนไหนผิดจริง — สมมติว่าทุกการแจ้งเตือนช่วงปกติเป็น false alarm
(ถ้ามีการโจมตีจริง Brain Power จะลดลง) → ทางแก้ระยะยาว: ให้คนกดยืนยันถูก/ผิดบนหน้าเว็บ

## กันไม่ให้การโจมตีจริงปลดความน่าเชื่อถือของ A (2026-10-09 13:01)

ปัญหา: นับทุกแจ้งเตือนเป็น false alarm → การโจมตีจริงทำให้ Brain Power ตก → ถ้าต่ำกว่า 50 แจ้งเตือนของ A กลับเป็น `low`
→ ข้อมูลช่วงโจมตีถูกนำไปเทรน (ผู้โจมตีใช้ปลดการป้องกันได้) แก้ 4 ข้อ:
1. A ได้รับความเชื่อถือแบบมี hysteresis: ถูกปลดเมื่อไม่ผ่านเงื่อนไข**ต่อเนื่อง 24 ชั่วโมง**เท่านั้น
2. false alarm ใช้**ค่ามัธยฐาน**ของอัตรารายชั่วโมงใน 6 ชั่วโมง (ทดสอบ: การโจมตี 2 ชั่วโมงได้ 1.0/ชม. แทน 12.8; โมเดลแจ้งผิดทุกชั่วโมงยังได้ 39.5)
3. ไม่นับ `A+B` เป็น false alarm
4. A ได้รับความเชื่อถือเมื่อ Brain Power ≥ 50 **และ** false alarm ≤ 5/ชม. (เดิมใช้แค่ Brain Power)

ไม่ใช้ปุ่มให้คนยืนยัน เพราะคนเฝ้าเองก็อาจไม่รู้ว่าถูกโจมตีจริงหรือไม่ — ทุกอย่างเป็นอัตโนมัติ
**กฎทั้งหมดสรุปไว้ที่ `detection_rules.md`**
